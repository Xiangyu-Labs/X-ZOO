- 本方案按这些文档写。

**现状（只读调查结果）：**

旧商城 `apps/uni-app`：

- 共 68 个页面：底部主页面 4 个，顾客页 47 个，店员页 15 个，死页 2 个。代码约 10.6 万行。
- 页面读的是 mapper 翻译出来的旧 snake_case 字段。

- 顾客接口 128 个，店员接口 36 个，webhook 4 个。
- 核心业务的契约基本干净。
- 为旧前端存在的部分：
  - `catalog.categoryVersion`、`catalog.skuPrice`、`cart.decrementItem`、`system.attachmentDataUrl`；

- **后端没有**：
  - 微信「小程序发货信息管理」（`upload_shipping_info`）；

- 主题表存在，但没有后台界面。

## 1. 技术栈推荐

| 层         | 选择                                                                                                                                              | 理由                                                                                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 框架       | **Taro 4（4.2.1）+ React 18 + TypeScript strict**，新建 `apps/mini`，纳入 pnpm workspace                                                          | 同一份代码编译出微信小程序（主目标）和 H5（开发副产品，用于 E2E 和预览）。和后台一样是 React + TS，团队只维护一种前端范式。京东维护，仍在活跃发布，MIT。                                                           |
| 数据层     | TanStack Query v5，外加少量 zustand（会话、购物车角标）                                                                                           | 后台已经在用 TanStack Query，缓存和失效的写法一致。需要为小程序接上 `useDidShow` 和网络状态这两个适配器。                                                                                                          |
| 接口客户端 | 新包 `packages/api-client`：**只 import 契约的类型**，外加由 `pnpm gen` 生成的「商城路由精简表」（id、method、path、auth）                        | 调研发现 `routes.gen.ts` 连带全部契约和 examples，约 886 KB，而且无法 tree-shake。只 import 类型可以保证：生产包里没有 zod、没有后台路由，也没有 `new Function`（小程序禁止）。开发和测试构建再对响应做 zod 校验。 |
| UI         | 自建一层薄的 UI kit（按钮、价格、卡片、空状态、骨架屏等）。弹层、选择器、Toast、日历这类复杂基础件用 **NutUI-React-Taro 3**（MIT），包在 kit 后面 | 业务组件都走自己的 kit，以后替换组件库只需改一处。                                                                                                                                                                 |
| 样式       | Sass modules + CSS 变量主题 token；设计稿宽 750，由 Taro 把 px 转成 rpx                                                                           | 装修主题 = 一组 token，页面根节点注入即可。                                                                                                                                                                        |
| 平台能力   | `apps/mini/src/platform/` 单点封装：登录、支付、分享、订阅消息、选地址、手机号、海报画布、隐私授权                                                | 页面不直接调 `Taro.*` 的平台 API（由守卫检查）。H5 构建有一个「模拟小程序」模式：发 `X-Client-Platform: wechat-mini`，用假 `wx.login` code，并通过假支付网关完成支付。这样 E2E 走的服务端路径和生产完全一样。      |

**没选的方案：**

- **原生小程序 + TS**：包最小、性能最好，但没有 H5。Playwright E2E 和装修的真实预览都得另写一套渲染器。
- **uni-app 3（Vue 3）**：技术栈和 React 后台分裂，装修组件没法和后台编辑器共用；测试生态也弱。它在 npm 上的 Vue 3 线仍然标着 alpha。

**已知代价：**

- Taro 的 React 插件只支持 **React 18**；后台是 React 19。两边共用的装修组件只能用 React 18 的 API，类型也按 18 固定。
- Taro 对 Node 24、TypeScript 7 和 pnpm 的兼容性，要在阶段 0 的试点里验证。

## 2. 装修（DIY v2）

### 2.1 数据模型（契约拥有，不背旧格式）

```
PageDocument = { schemaVersion: 2, root: { props: {标题, 背景, 分享文案…} }, blocks: Block[] }
Block        = { id, type, v, props }   // 有序数组；v 是这个块自己的版本，迁移函数写在 contracts
```

- **每个块的 props 是一个 zod schema**，用 zod 4 的 `.meta()` 带上编辑器元数据：标签、控件类型、分组。编辑器表单由它自动生成，不再手写面板。
- **所有块共享的基础属性**：间距（预设档位）、背景、圆角、可见性（受众、平台）。
- **数据源是声明式的**，例如 `{manual: ids} | {category, sort, limit} | {label, …}`。
  - 由服务端 resolver 一次性把「页面 + 每个块的数据」返回给小程序，减少请求。
  - 可缓存的公共数据，和按用户计算的状态（优惠券是否已领、是否符合新人资格）分开返回。
- **链接改成有类型的 `LinkTarget`**：`product | category | article | page | route(枚举) | webview | miniprogram`，不再存路径字符串。
  - 小程序页面路径只在一张映射表里维护。以后改页面路径，已保存的数据不会失效。
  - 这张表同时供小程序码、订阅消息、海报、通知链接使用，顺带修好 `/orders/{{orderId}}` 这类坏链接。
- **草稿和发布分开**：
  - 新表 `diy_documents` + 不可变的 `diy_revisions` + `published_revision_id` 指针；
  - 支持「保存草稿 / 发布 / 回滚到历史版本」；
  - 乐观锁沿用现有的版本冲突思路。
- **向前兼容**：客户端请求带 `X-Client-Version`；遇到不认识的块类型，resolver 或客户端直接跳过，老版本小程序不会崩。
- **旧装修数据不迁移**（生产上实际是空的），改为预置一套现代默认模板：首页、个人中心、一个微页面示例。

### 2.2 块清单（约 20 个，替代旧的 33 个）

| 页面         | 块                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 首页、微页面 | 搜索栏、轮播、导航宫格、图片魔方、热区图、公告、标题栏、商品列表（网格/列表/横滑）、商品选项卡、优惠券、新人券、拼团、预售、资讯、富文本、视频、间隔/分割线、悬浮客服、关注公众号 |
| 个人中心     | 用户卡片、订单入口、服务宫格；横幅复用轮播                                                                                                                                        |

去掉的旧组件：

- `homeComb`：改为组合现有块，再加一个「吸顶」设置；
- 旧版 `swipers`；
- `customComponent`（超级组件）；
- `member`：付费会员不在范围内；
- 商品详情的四件套和 `bottomMenu`；
- `pageFoot`。

### 2.3 编辑器：Puck（MIT，`@puckeditor/core` 0.23）+ 共用块组件

- 块组件**只写一次**，放在 `packages/storefront-blocks`。它们是纯展示的 Taro-React 组件，不调用任何 Taro API。
  - 小程序直接用。
  - 后台的 Puck 画布通过一层 `@tarojs/components` → DOM 的 shim 渲染同一份组件。
  - Puck 画布本身是 iframe。设成 375px 宽，再把同一份 Sass 编成 vw 单位，尺寸就能对上。
- Puck 提供开箱即用的画布拖拽、大纲、撤销/重做和属性栏。属性栏由 zod meta 生成；商品、分类、资讯、优惠券、链接的自定义字段复用后台现有的 antd 选择器。
- Puck 还没到 1.0：锁定版本，并包在我们自己的 `admin/decor` 模块后面，将来可以替换。
- **真实预览**：
  - 开发和 E2E 环境：编辑器旁边可以打开 Taro H5 构建的 iframe，用草稿 token 加载。
  - 生产环境：扫码在小程序体验版里预览草稿（依赖小程序账号就绪）。
- **后备方案**：如果阶段 0 的试点证明 shim 的像素还原度不达标，改用「antd 侧栏 + zod 自动表单 + Taro H5 iframe 预览（postMessage）」。数据模型不变。

### 2.4 不再装修的部分（页面形态改动，见第 5 节）

- **商品详情**：改为固定的精心设计页面，再加几个设置开关（是否显示评价、推荐、服务标签）。
- **底部导航**：4 个固定入口，只能改文字、图标、颜色。
- **分类页版式**：改为设置项。

## 3. 后端接口调整

**原则：**

- 采用「绞杀者」方式：开发期间**只新增、不破坏**，旧 uni-app 在 master 上继续可构建。到切换那次再统一删除。
- 订单、支付、退款、库存、优惠券、拼团、预售、鉴权的 service 和状态机**一律不动**。所有改动走契约 → service → 测试 → 守卫的流程。
- 契约的所有改动**由一个流（H）统一负责，先写契约**。客户端先对着 mock server 开发（它会用每个路由的第一个 example 应答）。

**新增或重做：**

| 项                                 | 内容                                                                                                                                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 启动配置                           | `GET /api/v1/app/config`（带 ETag），一次返回：站点信息、主题 token、底部导航、开关、各场景的订阅消息模板 ID、客服方式。取代由 mapper 拆分的 `site/config`。                              |
| 路由目录                           | 契约里的 `storefrontRoute` 枚举 → 小程序路径的唯一映射表。小程序码、订阅消息的 `page`、海报、通知链接、装修链接都从这里取。小程序码的 scene 编码/解码接口受 32 字节限制。                 |
| 静默登录                           | `wx.login` 拿到的 code，如果对应的 openid 已绑定账号，直接换 session。token 过期后无感续上，不必每次都弹授权。                                                                            |
| 头像昵称                           | 上传头像（有大小上限）并更新资料，配合 `chooseAvatar` 和 `type="nickname"` 输入框。                                                                                                       |
| 发票抬头                           | 新表 + CRUD；支持用 `wx.chooseInvoiceTitle` 导入。                                                                                                                                        |
| 下单的 `kindMeta`                  | 从 `Record<string, unknown>` 改为按 kind 区分的有类型联合（普通 / 拼团 / 预售）。**只改契约，核心逻辑不变。**                                                                             |
| 装修 v2                            | 后台接口：文档 CRUD、修订历史、发布、回滚、草稿预览 token、预览用的 resolve。商城接口：`GET /api/v1/pages/{home,user-center,:id}`，返回已 resolve 的块数据。                              |
| **发货信息管理**（小程序电商必需） | 通过 effects ledger 调用 `upload_shipping_info`（快递 / 虚拟等类型）、`set_msg_jump_path`、处理 `trade_manage_*` 推送，worker 负责重试。小程序端用确认收货组件（`wx.openBusinessView`）。 |
| **内容安全**                       | 评价文字和图片、昵称、发票抬头走 `msgSecCheck` / `mediaCheckAsync`。                                                                                                                      |
| 假实现                             | 以上用到的每个新微信接口，都在 `@shop/testing` 的 fake OA/mini server 里补假实现。                                                                                                        |

**切换时删除：**

- 旧装修的全部接口和后台旧编辑器；
- 只为旧前端存在的辅助接口（上面列的 7 个）；
- `MINI_CODE_PAGES` 等写死的旧路径；
- 如果你同意，再删 36 个店员接口和 `StaffCheck`。它们对应的 core service 如果后台也在用，就保留。

旧的数据库表**切换当次不 DROP**，因为回滚要求上一版镜像能在新 schema 上运行。下一次发布再按 OPS-007 的流程删。
（2026-09-24 改：切换改为一次发布，旧表在同一次发布里删，理由见 [cutover.md](cutover.md) 2.11。）

**保留不动：** 公众号和 H5 相关接口（`wechat-oa` 登录、jssdk、`wechat_h5` 支付通道）。它们不碍事、有测试、后台公众号功能也要用；新小程序只是不调用它们。

**发布后的兼容守卫：** 小程序会有旧版本长期留在用户手机上。第一次发布之后，新增一个检查：对比商城部分的 `openapi.json` 和上次发布的基线，发现破坏性改动就阻止合并。

## 4. 小程序平台必须满足的事（写进 `docs/mini/wechat-compliance.md`，并由守卫检查）

- **隐私：**
  - `app.json` 声明 `requiredPrivateInfos`，涉及 `chooseAddress` 等；
  - 实现 `onNeedPrivacyAuthorization` 和同意按钮；
  - 公众平台后台的隐私保护指引要逐项和代码对齐（手机号、地址、相册、剪贴板）。
- **登录：**
  - 允许不登录浏览；只在要下单、收藏这类动作时才要求登录；
  - 手机号快速验证是按次收费的，必须同时提供短信验证码作为替代。
- **订阅消息**：只能在用户点击时申请，每次最多 3 个模板。
- **包体积**：主包 ≤ 1.5 MB（微信上限 2 MB），总包 ≤ 8 MB（上限 20 MB），CI 按包设预算。
  - 主包只放 4 个底部页、商品详情、登录、隐私；其余按订单、售后、营销、账户、内容、微页面分包。
- **域名**：request、uploadFile、downloadFile 都必须 HTTPS 且已备案；web-view 只能打开已校验的业务域名。
- **类目和主体**：必须企业主体、完成小程序备案、绑定微信支付商户号、有电商类目。

## 5. 页面形态改动（功能保留，按小程序最佳实践重做）

| 旧                           | 新                                                                               | 原因                                                                 |
| ---------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 启动引导页（独立页面）       | 首页上的开屏广告浮层（用 `app/config` 里的 splashAd），可关闭或倒计时            | 小程序有原生启动画面，多跳一个页面会拖慢首屏，也和底部导航的跳转冲突 |
| 登录页（账号密码为主）       | 「手机号快速登录」为主，「短信验证码」为辅，密码登录放在「其他方式」；不强制登录 | 符合微信审核规则，也是最常见的最佳实践                               |
| 头像昵称来自授权             | `chooseAvatar` + 昵称输入框                                                      | `getUserProfile` 已被微信废弃                                        |
| 手填地址                     | 支持一键导入微信地址，也保留手填（地区选择器）                                   | 原生能力，下单更快                                                   |
| 发票抬头存在手机本地         | 存服务端，并支持从微信导入                                                       | 换手机不丢，多端一致                                                 |
| 客服（电话或二维码）         | 原生 `open-type="contact"` 客服会话，保留电话                                    | 原生能力                                                             |
| 确认收货按钮                 | 用微信的确认收货组件                                                             | 开通发货信息管理后必须这样做                                         |
| 内嵌网页可以打开任意 URL     | 只能打开已校验的业务域名，其他链接改为复制                                       | 平台限制                                                             |
| 商品详情页可装修             | 固定设计 + 设置开关                                                              | 旧的「可装修详情页」难用，数据也脆弱                                 |
| 分类页三种版式               | 一种现代版式（左侧一级类目、右侧网格），另设「是否显示二级类目」开关             | 精简                                                                 |
| 两个同名「退货列表」页面     | 合并为一个「售后」列表                                                           | 旧页面重复                                                           |
| 精品推荐（热卖、新品）分两页 | 一个页面，用 tab 切换                                                            | 精简                                                                 |
| 分享海报在 H5 上转 base64    | 用小程序 canvas 2D 绘制，图片走 downloadFile 域名                                | 不再需要 `attachmentDataUrl`                                         |

## 6. 测试与合并门（和上次重写同一标准）

- **单元 / 组件测试**：Vitest + Testing Library，放在 `apps/mini` 和 `packages/storefront-blocks`，配一个假 Taro 运行时（`@shop/testing/taro`）。
  - 块组件在 React 18 和 React 19 两个环境下各测一遍。
- **api-client**：对着 mock server 跑契约测试。
- **E2E**：Playwright，复用 `e2e/storefront` 的整套基座（Testcontainers、构建后的 web 和 worker、假支付网关、edge），在 Taro H5 的「模拟小程序」模式下跑。原有 spec 按新 UI 重写（page object）。
  - `docs/invariants.md` 里 SMOKE-* 和 DIY-* 规则引用的测试标题，要在同一个 PR 里同步更新。
- **后台**：装修编辑器的 Vitest 测试 + `e2e/admin` 新 spec（编辑、保存草稿、发布、回滚，并在商城端看到结果）。
- **构建检查**：
  - CI 构建 `mp-weixin` 并检查包体积预算；
  - 静态检查 `app.json`：页面存在、隐私声明齐全；
  - 扫描产物，不能出现 `eval` 或 `new Function`。
- **守卫**：`uniapp` 守卫换成 `mini` 守卫，检查：
  - 页面都存在；
  - 块注册表和契约一致；
  - 路由目录和页面一致；
  - 没有直接调用 `Taro.request` 或平台 API；
  - 没有退役词。
  - `retired` 和 `invariants` 守卫同步改路径。
- **小程序真机和 DevTools**：
  - 可选：本地用 `miniprogram-automator` 跑冒烟（需要 Windows 上的开发者工具，不进 CI）；
  - 真机按清单由人来测。
- **合并清单**：沿用 `docs/contributing.md`，加入 `apps/mini` 的 typecheck、lint、test、两端构建，以及新的 storefront E2E。

## 9. 主要风险

1. **Taro 在 Node 24、TS 7、pnpm 下的兼容性**，以及只支持 React 18。由 S1 验证；不过就降级工具链，或只在 `apps/mini` 内部固定版本。
2. **Puck + shim 的还原度**，以及 Puck 还没到 1.0。由 S3 验证；后备方案已经定好（iframe 预览）。
3. **主包体积**：React、reconciler、NutUI 加起来可能偏大。按需引入、分包，CI 设预算。
4. **外部资质和备案**进度不可控，会阻塞真机支付和上线。
5. **小程序没有进 CI 的真机自动化**。H5「模拟小程序」模式覆盖服务端路径；平台差异靠真机清单兜底。
6. **发布后接口兼容**：用 openapi 基线检查和 `X-Client-Version` 兜底。
7. **契约是共享地带**，多个流会同时要改。由 H 流统一负责、先写契约来规避冲突。
